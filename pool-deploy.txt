=======================

Instructions on how to deploy a BLNT v3 pool.

Source of truth for the v3 interface:
    blnt-contracts-v3/docs/V2_V3_PUBLIC_API.md
    blnt-contracts-v3/docs/V3_SYSTEM_SPEC.md

Older (v1/v2) references, still useful for the general flow:
    https://docs.blend.capital/pool-creators/tutorial-setting-up-a-pool
    https://app.sorobanhub.com
    https://raw.githubusercontent.com/Creit-Tech/SorobanHub-app/refs/heads/main/templates/project-views/blend/launch-pool.json

All commands below are mainnet.  Add `--send no` to any of them to
simulate first.

    inv() { stellar contract invoke --source-account alice \
              --network mainnet --inclusion-fee 10000000 --id "$@"; }

0. Oracle
---------

DECISION: deploy our own oracle aggregator.  Base USDC; every other asset
priced by Reflector's Stellar DEX feed; no pinned (base-like) assets.
Script: oracle/deploy-aggregator.sh (deploy, add-oracle, add-assets,
check).  Then:

    ORACLE=<id printed by `oracle/deploy-aggregator.sh deploy`>
    (deployed 2026-11-05: CDN7JD6SP32RZHB3DHK4S4AWCCQF6GYIUO455UCR4RGRZILZDRD24N36)

The oracle is fixed at deploy time (update_pool can't change it), so it
has to exist before step 1.

Pointing the pool straight at Reflector (no aggregator) was rejected: 14
decimals means min_collateral would be 5e14 for $5, no max_dev or max_age
checks, and the v3 auction math wasn't checked against 14 decimals.

What the v3 pool needs from an oracle (pool/src/pool/pool.rs): SEP-40
decimals() and lastprice(Asset::Stellar); price > 0 and timestamp less
than 24h old, else InvalidPrice and every action touching that asset
fails.  min_collateral and the $20 interest-auction minimum are in the
oracle's base (USDC here).

Check coverage of any oracle:
    inv $ORACLE --send no -- assets
    inv $ORACLE --send no -- lastprice --asset '{"Stellar":"<asset>"}'


1. Deploy the pool
------------------

    contract: pool factory
    function: deploy(admin, name, salt, oracle, backstop_take_rate,
                     max_positions, min_collateral, backstop_config,
                     access_controller) -> pool address

Changes from v1:
    * min_collateral (v2) - minimum collateral value per user, $5 on both
      reference pools.
    * backstop_config (v3) - ordered list of 0-3 tiers.  Order is the
      loss waterfall: FirstLoss, SecondLoss, ThirdLoss.  Each tier is
          {"asset": BlntXlm | BlntUsdc | Usdc | Xlm, "take_rate_weight": 1..100}
      BlntXlm and BlntUsdc may each appear once; Usdc/Xlm may repeat.
      Only the BLNT LP tiers earn BLNT emissions.
      IMMUTABLE.  An empty list = unbackstopped pool, which forces
      backstop_take_rate = 0 forever.
    * access_controller (v3) - optional; null = permissionless.

Salt is 32 random bytes as 64 hex chars:
    SALT=$(xxd -l32 -c 32 -ps /dev/random)

    inv $FACTORY -- deploy \
        --admin $U \
        --name "<pool name>" \
        --salt $SALT \
        --oracle $ORACLE \
        --backstop_take_rate 2000000 \
        --max_positions 6 \
        --min_collateral 50000000 \
        --backstop_config '[{"asset":"BlntXlm","take_rate_weight":4},{"asset":"BlntUsdc","take_rate_weight":3}]' \
        --access_controller null

    POOL=<returned address>
    (deployed 2026-11-05: YieldBlent CAUTPSQDAJEUV5XEU3EXFVYRGDJLEJGVTFJCFZCSPTDCREAMZ573VF4D)

(take rate and tiers above copy the existing BLNT pool, minus its Usdc
tier: DECISION 2026-11-05, BLNT LP tiers only.  The ybx v2 pool has a
take rate of 0.)


2. Reserves: queue_set_reserve + set_reserve (for each asset)
------------------------------------------------------------

A new pool starts in status 6 (setup).  While in setup there is no
timelock: set_reserve can be called right after queue_set_reserve.  Once
the status changes, a reserve change waits one week.

ReserveConfig has two fields that v1 didn't: `enabled` and `supply_cap`
(supply_cap is in the token's smallest units: 1e-7 for most, 1e-8 for SolvBTC).  util must be < max_util.

    inv $POOL -- queue_set_reserve --asset $ASSET --metadata '<json>'
    inv $POOL -- set_reserve --asset $ASSET          # returns res_index

c_factor / l_factor:
    effective collateral = value * c_factor
    effective liability  = value / l_factor
    health factor = effective collateral / effective liabilities, >= 1.0
    max borrow = collateral * c * l, so max LTV = c * l
    (XLM c 0.75 vs EURC l 0.90 -> 67.5%; USDC vs USDC 0.95/0.95 -> ~90%)
    c_factor 0 = can be supplied for interest but isn't collateral.
    Liquidation only below HF 1.0; a partial liquidation must leave the
    user between 1.03 and 1.15 (pool/src/auctions/user_liquidation_auction.rs).

Reserve configs for the new pool.  Based on the ybx v2 pool, with two
changes: c_factor = l_factor on every asset (ybx v2 had c_factor 0 on
EURC, AQUA, USDGLO, USTRY, CETES), and USDT0 and SolvBTC added.  AQUA, USTRY and

Thin-market collateral (AQUA, USTRY, CETES)
-------------------------------------------

The Feb 2026 ybx exploit: the USTRY/USDC SDEX book was empty, one 0.05
USTRY trade at ~$106.7 set Reflector's price, and USTRY collateral was
borrowed against for ~$10M.  Reflector now also counts AMM pool reserves,
so the price of these assets is mostly the depth of their Aqua pools.

Reflector changes (github.com/reflector-network/reflector-stellar-connector,
read 2026-11-03; latest release v4.3.0):
    2026-02-23  pool data aggregation and stable pool support (day after
                the exploit)
    2026-04-06  contract assets and Stellar classic liquidity pools
    2026-05-25  per-period volumes; MIN_VOLUME rescaled
    2026-10-09  Aqua and SushiSwap pools
How a 1-minute period is priced now: SDEX trades plus each AMM pool's
reserves counted as volume at the pool's implied price, summed into one
volume-weighted price.  Pool reserves are read at the last ledger before
the minute boundary.
Remaining gaps:
    * a pool counts if it has >= 100 units of base (USDC) reserve, a tiny
      floor.  An asset with no pool above it is priced from SDEX trades
      alone, i.e. exactly the Feb situation.
    * no outlier/median filter on trades.
    * a swap timed into the snapshot ledger still moves the price; it just
      costs capital in proportion to pool depth.
    * this is the code on GitHub; not verified which version the nodes run.

Exploit write-ups:
    https://www.halborn.com/blog/post/explained-the-yieldblox-hack-february-2026
    https://blocksec.com/blog/yieldblox-dao-incident-on-stellar-oracle-misconfiguration-enabled-a-10m-drain
    https://rekt.news/yieldblox-rekt
    https://x.com/script3official/status/2029289721114051073  (Script3 post-mortem)
    https://github.com/DK27ss/YieldBlox-10M-PoC

The supply cap is in TOKENS, so it limits how much can be deposited, not
the dollar loss.  For a price pushed to m times the real price:

    attacker profit ~= cap value * (m * c_factor * 0.95 - 1)
                       - cost of moving the Aqua pool by m

    break-even m = 1 / (c_factor * 0.95)   (borrowing USDC, l = 0.95)
        c 0.90 -> 1.17x    c 0.60 -> 1.75x    c 0.40 -> 2.63x

    cost of moving a constant-product pool by m ~= (sqrt(m) - 1) * USDC side
        USTRY/USDC ~$2.2M pool: 2x ~$455k, 3x ~$805k

Settings (Aqua depth 2026-11-03):

    asset  c=l   supply_cap (tokens)   ~value   main Aqua pool
    USTRY  0.60      70,000 (7e11)      $75k    USDC ~$2.2M
    CETES  0.60   1,200,000 (1.2e13)    $77k    USDC ~$2.3M
    AQUA   0.40     180M    (1.8e15)    $50k    XLM ~$1.3M, USDC ~$440k

Example: 200 USTRY (~$215) pushed to $100 -> 200*100*0.9 = $18k
collateral at c 0.90 -> ~$17.1k USDC borrowed, ~$16.9k bad debt (backstop
first).  The cap doesn't bind there.  Filling a ~$100k cap (92,850 USTRY)
at $100 -> ~$7.9M of borrowing power, i.e. the whole pool.  So a cap only
limits the loss together with something that limits m (pool depth,
max_dev, low c_factor).

At these caps a 2-3x push earns ~$10-55k and costs $450k+, so the attack
loses money.  Cost estimates assume a single constant-product pool and
ignore fees and the smaller pools Reflector also averages in (both make
the attack harder).  The caps also limit honest deposits (~$75k USTRY
total); raise them as Aqua depth grows (each change waits a week).
Lowering l with c (to keep c = l) makes borrowing these assets expensive
too (1/0.6 = 1.67x the debt).  The aggregator's max_dev (oracle/deploy-aggregator.sh)
also forces a slow ramp: it only compares consecutive 5-minute rounds,
so holding a price for two rounds passes it, but 2% steps take ~21
rounds (~1h45m) to reach 1.5x.

Re-check Aqua depth before deploy and periodically after.  If a pool
drains (the Feb trigger was the market maker pulling out), lower c/cap
(one-week timelock) or set_status 2/4 immediately.

    curl -s 'https://amm-api.aqua.network/pools/?size=500'
        (liquidity_usd looks like 7-decimal units)

3. Emissions
------------

    inv $POOL -- set_emissions_config --res_emission_metadata '[
        {"res_index":0,"res_type":0,"share":1000000}, ...]'

    res_type: 0 = liabilities (dTokens, borrowers),
              1 = supply (bTokens, lenders)
    share: 7 decimals, a JSON number (not a string).  Shares are relative
        weights: each is divided by the total of the enabled reserves'
        shares, so adding up to 1.0 (10000000) is only a convention.
        0 is rejected; each (res_index, res_type) may appear once.
    The whole config is replaced on each call.  No getter; read it with
        stellar contract read --network mainnet --id $POOL --key PoolEmis \
            --durability persistent --output string
    (map of reserve token id = res_index*2 + res_type -> share)

Emissions are BLNT.  The pool only gets them if it has a BlntXlm or
BlntUsdc backstop tier AND is in the backstop reward zone.  Entering
needs a positive BLNT LP deposit in its backstop (step 4), then
    inv $BACKSTOP -- add_reward --to_add $POOL     # omit --to_remove (None)
(V3_SYSTEM_SPEC.md 6.2; zone max 30 pools).  BLNT is split among
reward-zone pools by the BLNT inside each pool's backstop LP.

YieldBlent (DECISION 2026-11-05): USDC borrow 30%, XLM supply 20%, SolvBTC
supply 15%, EURC borrow 15%, PYUSD supply 10%, USDT0 supply 10%.
The BLNT v3 pool uses XLM supply 20%, USDC borrow 40%, EURC borrow 40%.


4. Backstop deposit (optional)
------------------------------

v3 deposits name a tier.  The tier must exist in the pool's
backstop_config, and the deposit token is that tier's asset (the BLNT LP,
USDC, or XLM), NOT the BLND/USDC Comet LP.

    inv $BACKSTOP -- deposit --tier FirstLoss --from $U --pool $POOL --amount <n>

Tiers: FirstLoss, SecondLoss, ThirdLoss.  Check with
    inv $BACKSTOP --send no -- pool_data --pool $POOL


5. Status
---------

    inv $POOL -- set_status --pool_status <n>

    0 admin active    1 active      2 admin on ice   3 on ice
    4 admin frozen    5 frozen      6 setup (initial state)

set_status only accepts 0, 2, 3, 4.  Statuses 1 and 5 are only reached
through update_status, driven by the backstop's queued-withdrawal ratio
(q4w_pct).  (pool/src/pool/status.rs)

There is NO minimum backstop value in v3 (the old 200k BLND/USDC
"product constant" threshold is gone).  The only gate is q4w_pct, the
value-weighted share of backstop deposits queued for withdrawal.

set_status allowed when:
    0 admin active     q4w < 50%
    2/3 on ice         q4w < 75%
    4 admin frozen     always

update_status transitions:
    admin active  -> on ice   at q4w >= 50%
    admin on ice  -> frozen   at q4w >= 75%
    active/on ice/frozen      >= 60% frozen, >= 30% on ice, else active
    setup and admin frozen can't be changed by update_status

Leaving setup (6) starts the one-week timelock on any later reserve
change (step 2), so finish adding reserves first.

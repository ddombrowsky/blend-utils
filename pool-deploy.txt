0. Oracle
---------

The oracle is fixed at deploy time (update_pool can't change it), so pick
it first.

The two existing oracles do NOT cover the same assets:

    CD74A3C5...MXXR  (ybx)   base USDC.  Prices all 8 ybx reserves.
                             USDC, USDGLO, PYUSD are pinned at 1.0.
    CCVTVW2C...POATS (BLNT)  base USD.  Prices ONLY XLM, USDC, EURC
                             (see `assets`).  lastprice errors for AQUA,
                             USDGLO, USTRY, CETES, PYUSD.

Options:
    a. use the ybx oracle as-is (depends on its operator)
    b. deploy our own `oracle-aggregator` (~/work/script3/blend/oracle-aggregator)
       covering the extra assets
    c. launch with XLM/USDC/EURC only on the BLNT oracle

Check coverage of a candidate oracle:
    inv $ORACLE --send no -- assets
    inv $ORACLE --send no -- lastprice --asset '{"Stellar":"<asset>"}'

    ORACLE=<chosen oracle>


1. Deploy the pool
------------------

    contract: pool factory
    function: deploy(admin, name, salt, oracle, backstop_take_rate,
                     max_positions, min_collateral, backstop_config,
                     access_controller) -> pool address

Changes from v1:
    * min_collateral (v2) - minimum collateral value per user, $5 on both
      reference pools.
    * backstop_config (v3) - ordered list of 0-3 tiers.  Order is the
      loss waterfall: FirstLoss, SecondLoss, ThirdLoss.  Each tier is
          {"asset": BlntXlm | BlntUsdc | Usdc | Xlm, "take_rate_weight": 1..100}
      BlntXlm and BlntUsdc may each appear once; Usdc/Xlm may repeat.
      Only the BLNT LP tiers earn BLNT emissions.
      IMMUTABLE.  An empty list = unbackstopped pool, which forces
      backstop_take_rate = 0 forever.
    * access_controller (v3) - optional; null = permissionless.

Salt is 32 random bytes as 64 hex chars:
    SALT=$(xxd -l32 -c 32 -ps /dev/random)

    inv $FACTORY -- deploy \
        --admin $U \
        --name "<pool name>" \
        --salt $SALT \
        --oracle $ORACLE \
        --backstop_take_rate 2000000 \
        --max_positions 6 \
        --min_collateral 50000000 \
        --backstop_config '[{"asset":"BlntXlm","take_rate_weight":4},{"asset":"BlntUsdc","take_rate_weight":3},{"asset":"Usdc","take_rate_weight":2}]' \
        --access_controller null

    POOL=<returned address>

(take rate and tiers above copy the existing BLNT pool; the ybx v2 pool
has a take rate of 0.)


2. Reserves: queue_set_reserve + set_reserve (for each asset)
------------------------------------------------------------

A new pool starts in status 6 (setup).  While in setup there is no
timelock: set_reserve can be called right after queue_set_reserve.  Once
the status changes, a reserve change waits one week.

ReserveConfig has two fields that v1 didn't: `enabled` and `supply_cap`
(supply_cap is in 7-decimal token units).  util must be < max_util.

    inv $POOL -- queue_set_reserve --asset $ASSET --metadata '<json>'
    inv $POOL -- set_reserve --asset $ASSET          # returns res_index

changes: c_factor = l_factor on every asset (ybx v2 had c_factor 0 on

3. Emissions
------------

    inv $POOL -- set_emissions_config --res_emission_metadata '[
        {"res_index":0,"res_type":0,"share":"1000000"}, ...]'

    res_type: 0 = liabilities (dTokens, borrowers),
              1 = supply (bTokens, lenders)
    share: 7 decimals, shares should add up to 1.0 (10000000)

Emissions are BLNT.  The pool only gets them if it has a BlntXlm or
BlntUsdc backstop tier.


4. Backstop deposit (optional)
------------------------------

v3 deposits name a tier.  The tier must exist in the pool's
backstop_config, and the deposit token is that tier's asset (the BLNT LP,
USDC, or XLM), NOT the BLND/USDC Comet LP.

    inv $BACKSTOP -- deposit --tier FirstLoss --from $U --pool $POOL --amount <n>

Tiers: FirstLoss, SecondLoss, ThirdLoss.  Check with
    inv $BACKSTOP --send no -- pool_data --pool $POOL


5. Status
---------

    inv $POOL -- set_status --pool_status <n>

    0 admin active    1 active      2 admin on ice   3 on ice
    4 admin frozen    5 frozen      6 setup (initial state)

set_status only accepts 0, 2, 3, 4.  Statuses 1 and 5 are only reached
through update_status, driven by the backstop's queued-withdrawal ratio
(q4w_pct).  (pool/src/pool/status.rs)

There is NO minimum backstop value in v3 (the old 200k BLND/USDC
"product constant" threshold is gone).  The only gate is q4w_pct, the
value-weighted share of backstop deposits queued for withdrawal.

set_status allowed when:
    0 admin active     q4w < 50%
    2/3 on ice         q4w < 75%
    4 admin frozen     always

update_status transitions:
    admin active  -> on ice   at q4w >= 50%
    admin on ice  -> frozen   at q4w >= 75%
    active/on ice/frozen      >= 60% frozen, >= 30% on ice, else active
    setup and admin frozen can't be changed by update_status

Leaving setup (6) starts the one-week timelock on any later reserve
change (step 2), so finish adding reserves first.

## automated auction bot

source:
    https://github.com/script3/auctioneer-bot

docker:
    docker pull script3/auctioneer-bot:latest

config.json:
* `defaultProfitPct` is from 0.00 to 1.00, 0.1 = 10%.
* `minHealthFactor` 0 to inf, 1.1=110%.  Equal to collateral / liabilities.
  Note that this the HF for the _bidding_ bot.  The collateral and liabilities are
  transfered directly to the bidding bot, so the HF of the bot's account
  needs to be high enough to handle that.  That means it should already have significant
  collateral in the bank.  The HF is calculated including the fillers existing deposits.
* example (v1):
  https://github.com/script3/auctioneer-bot/blob/main/example.config.json
* for auctions, lot values move 0.005 (0.5 basis points) per block for the first 200 blocks,
  then bid value moves down 0.006 after that.  So any change less than that will not
  affect the block the bidder goes for.

## creating BLNT v3 interest auctions

    ~/work/script3/blend/blend-utils/auction/new-interest-v3.sh

For each v3 pool (fixed CACSQWCMKG45TUHCQ3LXHOB7YEEJH4W376ZHQPXH2IZ3TE4NJHFZMCY7
and yieldblent CAUTPSQDAJEUV5XEU3EXFVYRGDJLEJGVTFJCFZCSPTDCREAMZ573VF4D) it
runs interest-v3.py, which reads every reserve's accrued backstop_credit,
picks the 4 reserves with the most credit in USD as the lot (v3 lots max out
at 4), and calls `new_auction` (auction_type 2 = interest auction, percent
100) on mainnet, signed by the `xbull` key.  Output goes to auction.log.
Add a pool by adding a name=address line to new-interest-v3.sh.
`./new-interest-v3.sh --dry-run` simulates instead of sending.

If it fails with Error #1228 (not enough interest accrued yet), it prints
each tier's accrued credit per asset.  A single backstop tier's share of
the lot has to be worth at least $20 before an auction can be created.
Other errors: #1200 = bad request (wrong user / percent != 100),
#1212 = auction in progress, #1227 = invalid interest auction.

Run it in a loop until an auction gets created:

    ( while true ; do date ; ./new-interest-v3.sh ; sleep 300 ; done ) 2>&1 | tee log

### how the backstop tier is chosen (lower tiers are not starved)

From blnt-contracts-v3/pool/src/auctions/tier_interest.rs:

* Each auction creation splits newly accrued backstop_credit across the three
  tiers, weighted by tier value * take_rate_weight, into a per-asset running
  balance (first_loss / second_loss / third_loss).  A tier's balance is only
  reduced when that tier's auction is filled, so a skipped tier keeps
  accumulating until it reaches $20.
* Tier selection is round-robin: select_interest_tier starts at a cursor and
  picks the first tier with >= $20 (MIN_AUCTION_LOT_VALUE_USDC), wrapping
  around.  After an auction the cursor moves to the next tier.  So a small
  tier gets checked first every round until it crosses $20.
* Smaller tiers auction less often, in proportion to their share (a tier
  with 10% of the take rate takes ~10x as long to reach $20).
* Tiers with backstop value 0 are skipped and get no allocation.
* The $20 check sums a tier's balance across only the assets in --lot, so
  include every asset with accrued credit.

new-interest.sh is the Blend v2 equivalent (ybx v2 and other v2 pools, lots
of up to 5 assets).

## BLNT v3 liquidation test (2026-11-01)

The bot runs on a separate local machine, docker container
auction6, data in ~/work/blend/blend-utils/auction/data-v3/ (auctioneer.sqlite
has per-user health_factor in the `users` table; logs/ has main, worker,
bidder logs).

Liquidation rules (pool/src/auctions/user_liquidation_auction.rs):
* Only allowed when liabilities > collateral (HF < 1.0), after c_factor /
  l_factor.  The bot creates one when HF < 0.998 (isLiquidatable).
* A partial liquidation must leave the user with HF between 1.03 and 1.15.
* Borrows are refused below HF 1.00001 (pool/submit.rs), so the closest you
  can load an account is just over 1.0.
* The bot rechecks users under HF 1.2 every ~100 min ("Scanning N users", N
  includes the backstop) and on price changes.

Test: loaded the xbull account (GDJSH2NU..., XLM collateral, EURC debt) to
HF ~1.001 by borrowing EURC with `submit` (request_type 4 = Borrow, amount
in 7-decimal units):

    U=GDJSH2NU2WF6J4P5DL4522DUCABWSTZOKFQ7BHBCFYQ3QKC6FRYWP6OL
    stellar contract invoke \
      --id CACSQWCMKG45TUHCQ3LXHOB7YEEJH4W376ZHQPXH2IZ3TE4NJHFZMCY7 \
      --source-account xbull --network mainnet --fee 10000000 -- \
      submit --from $U --spender $U --to $U \
        --requests '[{"request_type":4,"address":"CDTKPWPLOURQA2SGTKTUQOWRCBZEORB4BWBOMJ3D3ZTQQSGE5F6JBQLV","amount":"599397"}]'

Add `--send no` to simulate first.  Amount to borrow for a target HF:
  eff_coll = XLM bTokens * b_rate/1e12 * XLM price * 0.75
  eff_liab = EURC dTokens * d_rate/1e12 * EURC price / 0.95
  borrow EURC = (eff_coll/target - eff_liab) * 0.95 / EURC price
(get_positions / get_reserve on the pool, lastprice on oracle
CCVTVW2CVA7JLH4ROQGP3CU4T3EXVCK66AZGSM4MUQPXAI4QHCZPOATS).  It took two
borrows because XLM rose against EURC after the first one.
